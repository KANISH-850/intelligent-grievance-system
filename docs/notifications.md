# Notification System Architecture & Integration Guide

## Overview

Phase 9 introduces a persistent, in-app notification framework for the **Intelligent Multilingual Grievance Categorization and Automated Dispatch Framework**.

The notification system alerts citizens, department officers, and administrators about key events in a grievance's lifecycle (submission, assignment, status changes, resolution, rejection, and priority escalation).

---

## 1. Database Model

The system utilizes the Prisma `Notification` model:

```prisma
enum NotificationType {
  GRIEVANCE_SUBMITTED
  GRIEVANCE_ASSIGNED
  STATUS_CHANGED
  HIGH_PRIORITY
  CRITICAL_PRIORITY
  GRIEVANCE_RESOLVED
  GRIEVANCE_REJECTED
}

model Notification {
  id           String           @id @default(uuid())
  user_id      String
  grievance_id String?
  type         NotificationType
  title        String
  message      String
  is_read      Boolean          @default(false)
  created_at   DateTime         @default(now())

  user      User       @relation(fields: [user_id], references: [id], onDelete: Cascade)
  grievance Grievance? @relation(fields: [grievance_id], references: [id], onDelete: SetNull)

  @@index([user_id])
  @@index([is_read])
  @@map("notifications")
}
```

---

## 2. Notification Triggers & Workflows

Notifications are automatically generated by backend services within atomic Prisma transactions during key events:

| Event | Target Role / Recipient | Notification Type | Trigger Location |
|---|---|---|---|
| Grievance Submitted | Citizen | `GRIEVANCE_SUBMITTED` | `grievance.service.js` |
| High Priority Detected (`HIGH`) | Department Officers | `HIGH_PRIORITY` | `grievance.service.js` |
| Critical Priority Detected (`CRITICAL`) | Admin & Department Officers | `CRITICAL_PRIORITY` | `grievance.service.js` |
| Officer Assigned | Assigned Officer | `GRIEVANCE_ASSIGNED` | `officer.service.js` / `admin.service.js` |
| Status Changed (`IN_PROGRESS`) | Citizen Owner | `STATUS_CHANGED` | `officer.service.js` / `admin.service.js` |
| Grievance Resolved (`RESOLVED`) | Citizen Owner | `GRIEVANCE_RESOLVED` | `officer.service.js` / `admin.service.js` |
| Grievance Rejected (`REJECTED`) | Citizen Owner | `GRIEVANCE_REJECTED` | `officer.service.js` / `admin.service.js` |

## 3. Backend API Endpoints

All notification endpoints require JWT authentication.

### `GET /api/v1/notifications`
- **Description:** Retrieve caller's notifications.
- **Query Params:** `unreadOnly` (boolean, optional), `limit` (integer, default: 20)
- **Response:**
  ```json
  {
    "status": "success",
    "data": {
      "notifications": [ ... ],
      "unreadCount": 3
    }
  }
  ```

### `PATCH /api/v1/notifications/:id/read`
- **Description:** Mark a specific notification as read. User must own the notification.
- **Response:** Updated notification object.

### `PATCH /api/v1/notifications/read-all`
- **Description:** Mark all unread notifications for the caller as read.
- **Response:** Number of updated records.

## 4. Frontend Integration & Polling

- **Component:** `NotificationDropdown.tsx` situated in `DashboardLayout.tsx`.
- **Mechanism:** Periodically polls `GET /api/v1/notifications` every 20 seconds while authenticated.
- **UI Elements:** Interactive bell icon with animated badge showing unread count, scrollable list, time formatting (e.g., "5m ago"), mark as read buttons, and direct link to the corresponding grievance detail page.

---

## 5. Security & Isolation

1. **Strict Ownership Control:** Users can only query or modify notifications matching their authenticated `req.user.id`.
2. **Input Sanitization:** Notification titles and messages do not reflect unvalidated input.
3. **No Cross-User Leaks:** Department alerts fetch department officer user IDs securely from the database.
